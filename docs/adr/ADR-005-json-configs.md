# ADR-005. Data-driven конфиги: JSON, схема, валидация, отсутствие фолбэков

**Статус:** предложен (ожидает Human-Gate M0)
**Дата:** 2026-11-08
**Связано:** `docs/prototype-plan.md` (M3, M9), ADR-001

## Контекст

План запрещает хардкод геймплейных параметров (урон, дальность, кулдаун, скорость, время респавна) в коде: параметры живут в конфигах, изменение конфига меняет поведение без правки кода. Один и тот же файл обязан читать сервер (.NET 10) и клиент (Unity 6.3, M9), иначе предсказание на клиенте разойдётся с сервером.

Требования: читаемость человеком, валидация до старта симуляции, понятная ошибка при ошибке в конфиге, невозможность «тихого» дефолта вместо параметра.

## Решение

1. **Формат — JSON** (`System.Text.Json`, `Shared.Config`). Файлы — в `config/` в корне репозитория; при сборке клиента копируются в `StreamingAssets` (M9), сервер читает их из рабочей директории (путь — параметр запуска).
2. **Наборы:** `config/actors.json` (тип актора: `id`, `maxHp`, `moveSpeed`, `maxResource`, `resourceRegenPerSecond`, `respawnSeconds`), `config/abilities.json` (`id`, `damage`, `range`, `cooldownSeconds`, `resourceCost`, ссылка на актора/эффект). Минимально необходимый набор для M3; расширение — по задачам плана, не «на всякий случай».
3. **DTO — простые `record`-классы в `Shared.Config`** без логики; загрузчик (`ConfigLoader`) валидирует и возвращает иммутабельный снимок (`GameConfig`), который получает `Simulation.Core` через конструктор. Симуляция не читает файлы.
4. **Валидация (fail-fast, до первого тика):**
   - уникальность `id` в пределах набора;
   - числовые диапазоны: `maxHp > 0`, `moveSpeed > 0`, `maxResource >= 0`, `resourceRegenPerSecond >= 0`, `damage >= 0`, `range >= 0`, `cooldownSeconds >= 0`, `respawnSeconds >= 0`;
   - ссылочная целостность: `abilities[].actorId` существует в `actors`;
   - запрет `NaN`/`Infinity`, запрет неизвестных полей (`JsonSerializerOptions` с `UnmappedMemberHandling.Disallow`).
   Ошибка → исключение `ConfigValidationException` с **путём к файлу, полем и значением**, а не «config is invalid».
5. **Никаких фолбэков.** Отсутствующий файл, отсутствующее поле, нулевое значение → ошибка запуска. Тест M3 «удалить JSON → должно упасть, а не взять дефолт» — часть контракта.
6. **Секунды в конфиге, тики в симуляции.** Конвертация — один раз в загрузчике: `ticks = (int)MathF.Round(seconds * TickRate, MidpointRounding.AwayFromZero)`; результат конвертации виден в `GameConfig` и покрыт тестом на округление (0.05 с → 1 тик, 0.025 с → 1 тик).
7. **JSON Schema** (`config/*.schema.json`) — для IDE и ревью; рантайм-валидация — код, не схема (схема не должна становиться вторым источником истины).
8. **Хеш конфигов** пишется в лог старта сервера и клиента; тест M9 сверяет, что клиент и сервер используют один и тот же файл.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| `ScriptableObject` (Unity) | Сервер (без Unity) не может их прочитать — нарушает ADR-001 и M9 |
| YAML/TOML | Хуже инструменты в .NET и Unity, нет преимуществ |
| Захардкоженные константы | Прямо запрещено планом и `AGENT.md` §11 |
| JSON Schema как единственный валидатор | Нужен рантайм-валидатор с понятными ошибками; схема дублирует правила |
| `IOptions`/конфигурация ASP.NET | Лишняя инфраструктура и неявные фолбэки (значения по умолчанию) — ровно то, что запрещено |

## Последствия

- Изменение баланса = правка JSON (+ тест), без пересборки; это и есть проверяемое свойство M3.
- Тесты, зависящие от чисел, параметризуются от конфига, а не дублируют константы; «изменил JSON → тест изменился» — обязательный тест M3.
- Загрузчик — единственное место с `System.Text.Json`; `Simulation.Core` о JSON не знает.
- Ошибка в конфиге обнаруживается на старте, а не в бою; сервер не запускается с невалидным конфигом.
- На клиенте конфиг обязан быть тем же файлом (хеш в тесте M9), иначе предсказание будет расходиться — это ловится тестом, а не ревью.
