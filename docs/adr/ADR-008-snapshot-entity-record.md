# ADR-008. Запись сущности в снапшоте и версия протокола 2

**Статус:** принят в M4 (требует подтверждения на Human-Gate M4)
**Дата:** 2026-11-09
**Связано:** ADR-004 (формат снапшотов), ADR-006 (реконсиляция), `docs/prototype-plan.md` (M4, M6)

## Контекст

ADR-004 задал эскиз записи сущности: `id`, `x,y,z`, `hp`, `flags`. К моменту M4 у `EntityState` появились поля, без которых клиент не может ни отрисовать состояние, ни восстановить симуляцию для реконсиляции (ADR-006): тип актора, точка появления, ресурс и его максимум, тик окончания кулдауна, тик респавна. Отправлять их отдельным сообщением — значит плодить второй формат и второй источник рассинхрона.

Кроме того, M4 — первый момент, когда формат реально реализован в байтах. До этого «заморозка» ADR-004 была эскизом без кода.

## Решение

Запись сущности в полном снапшоте (little-endian, 57 байт):

| Поле | Тип | Примечание |
|---|---|---|
| `id` | `uint32` | идентификатор сущности |
| `actorId` | `uint32` | тип актора — нужен для восстановления статов из конфига |
| `x, y, z` | `float32` ×3 | позиция; NaN/Infinity запрещены при записи и чтении |
| `spawnX, spawnY, spawnZ` | `float32` ×3 | точка респавна |
| `hp` | `int32` | текущее здоровье |
| `maxHp` | `int32` | максимум здоровья |
| `resource` | `int32` | текущий ресурс |
| `maxResource` | `int32` | максимум ресурса |
| `cooldownUntilTick` | `uint32` | тик окончания кулдауна |
| `respawnAtTick` | `uint32` | тик респавна (0 — жив) |
| `flags` | `byte` | bit0 — `isDead` |

Тело снапшота: `tick uint32`, `entityCount uint16`, далее `entityCount` записей. Заголовок сообщения — из ADR-004 (`magic`, `protocolVersion`, `messageType`, `payloadLength`).

**`Protocol.Version` поднимается до 2.** Причина — формат впервые реализован и отличается от эскиза ADR-004; несовпадение версий при handshake обязано отклонять соединение (M5).

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Отправлять только `id/x/y/z/hp/flags` из эскиза | Клиент не знает `actorId` → не может восстановить статы и кулдаун; реконсиляция в M6/M9 потребует второго канала |
| Отдельное сообщение «статы сущности» | Два источника правды и лишний handshake на каждого актора |
| Строки/JSON для «редких» полей | Размер и аллокации при 20 Гц; разный парсинг на Unity и .NET |
| Не поднимать версию, «договориться» | Рассинхрон станет тихим — прямо запрещено ADR-004 |

## Последствия

- Клиент (M6) получает из снапшота всё, что нужно для отрисовки и реконсиляции без дополнительных запросов.
- Размер снапшота: 6 + 57·N байт; при 20 сущностях ≈ 1.1 КБ на снапшот, 22 КБ/с на клиента — в бюджете 50 мс и полосе прототипа.
- Roundtrip-тесты и границы (0 сущностей, `uint.MaxValue`, NaN) закреплены в `SnapshotSerializerTests`.
- Дельта (M8) будет передавать эту же полную запись для изменённых сущностей — состав полей менять не придётся.
- Изменение состава полей — только новой версией протокола и правкой этого ADR.
