## 3. Форматы

### 3.1 Задача в `docs/plan_for_gemma.md`

```
## T-012 — [короткое название]

- [ ] статус: ожидает
- Цель: одно проверяемое поведение.
- Файлы: `путь/файл.cs` (максимум 2 файла).
- Контекст: классы/символы, которые надо прочитать (через grep/trail, не весь файл).
- Ограничения: что нельзя менять (AGENTS.md + локальные).
- Критерии приёмки: как проверить (тест/поведение/лог).
- Гейты: `dotnet build`, `dotnet test`, Unity compile.
- Промпт для gemma: готовый текст, без домыслов.
- Размер: ≤2 файла, ≤150 строк изменений.
- Зависимости: T-00X или «нет».
```

Правило нарезки: не влезает в лимиты — дели на две задачи, лимит не расширяй.

### 3.2 Отчёт `reports/<ID>.md`

Сделано (2–5 строк) · изменённые файлы · гейты · вердикт ревью · чек-лист
пользователю (3–7) · путь к билду · расход (вызовы, $).

### 3.3 Вердикт ревьюера — только JSON

```json
{ "verdict": "PASS|FAIL", "must_fix": ["..."], "risk": "low|medium|high", "notes": "1-2 строки" }
```

## 4. `gates.ps1` — состав

По порядку, стоп на первом провале, в конце JSON
`{ "ok": bool, "failed_step": "...", "tail": "последние 40 строк лога" }`.

1. `dotnet build Prototype.sln -c Release --nologo -v:q` (таймаут 10 мин).
2. `dotnet test src/Tests/Tests.csproj --no-build -c Release` (таймаут 10 мин).
3. `bash tools/ci/check-architecture.sh` и `check-unity-boundaries.sh`; bash нет —
   WARN, не блокировать.
4. Unity compile: env `UNITY_EDITOR_PATH` → Unity Hub → стандартные пути; проверить,
   что `Unity.exe` не запущен (иначе «закрой редактор»); затем
   `Unity.exe -batchmode -quit -projectPath unity-client -logFile <tmp>\unity-compile.log`
   (таймаут 20 мин). Код 0 — ок, иначе вытащить `error CS` / `Compilation failed`.

Логи — `reports/logs/<task>-<step>.log`, в JSON только хвост.

## 5. Оркестратор `tools/tandem/orchestrator.workflow.js`

Целевой цикл:

```
взять первую задачу с "[ ]"
для каждой задачи:
  ветка agent/T-<slug> от main
  attempts = 0
  цикл: attempts++; executor(gemma) → gates; ok → выход;
        attempts == 3 → эскалация
  reviewer(deepseek): FAIL и attempts < 4 → must_fix и повтор;
        FAIL и attempts == 4 → debugger(deepseek) → одна попытка gemma;
        снова FAIL → стоп, notify (если away), отчёт «блокер»
после задач: build-windows.ps1 → exe → architect → reports/<фича>.md,
             чекбоксы, spend.jsonl, notify (только при .agent/away)
```

**Важная поправка по факту:** тело DSH-workflow не имеет ни файловой системы,
ни сети, ни shell. Поэтому чтение `plan_for_gemma.md`, `git checkout -b` и запуск
`gates.ps1` делают агенты (у них есть инструменты), а скрипт только раскладывает
фазы и принимает решения по их структурированным ответам. Задачи приходят
в скрипт через `args`, распарсенные вызывающим агентом; промпты ролей передаются
**путями** (`promptFiles`), чтобы не гнать их текст через контекст вызывающего.

Порядок шагов одной задачи (итоговый): исполнитель + быстрые гейты (`-SkipUnity`)
→ ревью → **полный** гейт с Unity → следующий шаг. Unity-компиляция (~71 с на этом
хосте) стоит после ревью намеренно: незачем тратить минуту на код, который ревью
всё равно вернёт.

Правила: не мержить и не пушить в `main`; не трогать файлы вне задачи; перед каждым
платным вызовом сверяться со `spend.jsonl`, при превышении cap — стоп и отчёт.

## 6. Промпты ролей

- `architect.md` — интервью списком с вариантами, план по 3.1, ADR при архитектурном
  решении, чек-лист playtest; код не пишет.
- `executor.md` — строго по задаче, читает только указанные символы, минимальный дифф,
  сам гоняет быстрые гейты, в конце перечисляет изменённые файлы.
- `reviewer.md` — только diff + логи; API существует, null-пути, аллокации в `Update`,
  сериализация, порядок инициализации, соответствие AGENTS.md; ответ строго JSON (3.3);
  код не переписывает.
- `debugger.md` — попытки + логи + релевантный код; диагноз и пошаговый план;
  не более 15 строк кода в ответе.

## 7. `notify.ps1`

Читает `.agent/telegram.json`, POST `https://api.telegram.org/bot<token>/sendMessage`
(chat_id + text), таймаут 10 с, 2 попытки. Fallback: `curl.exe`, затем `node`.
Полный провал — строка в `reports/tandem.log`, скрипт не падает. Без `.agent/away`
ничего не отправляет (кроме явного `-Force` для проверки).

## 11. Риски

- Unity batchmode: занятый редактор, лицензия, долгий импорт → таймауты и понятные ошибки.
- bash на Windows может отсутствовать → гейт 3 не блокирует.
- gemma «плывёт» на tool calling → fallback из 9.1.
- Долгие сборки → логи в `reports/logs/`, хвост не терять.
- `.agent/away` конфликтует с git → держать в `.gitignore`.

### Поправки к плану, найденные по факту

1. **Workflow-скрипт не имеет fs/shell** — план, git и гейты выполняют агенты;
   промпты передаются путями (`promptFiles`), а не текстом (§5).
2. **Схемы `agent()` требуют `type` у `enum`** — иначе рантайм отвергает вызов
   до первого шага (первая попытка пилота упала именно так).
3. **bash на этом хосте** — только Git Bash; WSL-заглушка `WindowsApps\bash.exe`
   не годится (пути `/mnt/f`, `set -o pipefail` падает). Добавлено правило
   `*.sh text eol=lf` в `.gitattributes`.
4. **Unity пишет «Exception:» и при успехе** — детектор ошибок сужен до
   `error CS####` / `Compilation failed` / `Scripts have compiler errors`.
5. **`api.telegram.org` не отвечает из curl/IRM на этом хосте**, работает node —
   порядок доставки: node → curl → IRM.
6. **ADR нумеруются до 025**, поэтому новый — ADR-026 (в плане было «с 013»).
7. **CI строже локального гейта** — выровнено 22.11.2026: `gates.ps1` гоняет
   `dotnet test` с теми же флагами, что `.github/workflows/ci.yml`
   (`/p:Threshold=100` по `[Simulation.Core]Simulation.Core.Simulation`).
   `-SkipCoverage` оставлен для быстрого локального прогона.
8. **Ветки пересобраны от `origin/main`** (`b75184f`), а не от локального
   `main` (`99b12ae`, +71 коммит): иначе пуш тащил бы 71 непубликованный коммит.
   Побочный эффект: на этой базе нет `AGENTS.md` (файл появился позже), поэтому
   в первом коммите он создаётся целиком — см. историю ветки.
