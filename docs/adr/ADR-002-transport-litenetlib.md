# ADR-002. Транспорт: LiteNetLib 2.1.4 против Netcode for GameObjects и Mirror

**Статус:** предложен (ожидает Human-Gate M0)
**Дата:** 2026-11-08
**Связано:** `docs/prototype-plan.md` (M4, M5, M8), ADR-004

## Контекст

Нужен UDP-транспорт между `src/Server` (консольный .NET 10) и Unity-клиентом, который:

- доставляет **команды** надёжно и по порядку (потеря ввода недопустима);
- доставляет **снапшоты** ненадёжно (устаревший снапшот бесполезен, ждать его переотправки вредно);
- умеет фрагментировать пакеты (снапшот больше MTU);
- позволяет отклонить соединение при несовпадении версии протокола;
- не диктует архитектуру: симуляция уже отделена (ADR-001), транспорт — сменный адаптер за `ITransport`;
- работает в headless-тестах на Linux и в Unity 6.3 LTS без правок.

Целевой масштаб — 10–20 CCU (M11: 20 ботов), то есть производительность не является ограничением; важнее простота, предсказуемость и объём кода, который агент способен удержать в контексте.

## Решение

**LiteNetLib 2.1.4 из NuGet**, за абстракцией `ITransport` (`src/Shared`/`src/Client.Network`).

- `src/Client.Network/LiteNetLibTransport` реализует `ITransport` (подключение, отправка сообщения, приём, событие отключения).
- Команды — `DeliveryMethod.ReliableOrdered`.
- Снапшоты — `DeliveryMethod.Unreliable`; полный снапшот по запросу/таймауту — `ReliableOrdered`.
- Абстракция `ITransport` не протекает типами LiteNetLib: наружу — только `ReadOnlyMemory<byte>`/`byte[]` и наши enum'ы.
- Версия протокола передаётся в handshake-данных подключения; несовпадение → отказ с причиной (тест в M5).
- Пакет — только через NuGet; вендоринг исходников запрещён решением оператора.

**Проверить в M1/M5 (не выдумывать API):** целевые фреймворки пакета (`netstandard2.0/2.1`) и совместимость с Unity 6.3; актуальные имена классов для `NetManager`, `EventBasedNetListener`, `NetPacketProcessor`, `NetDataWriter`; поведение `Unreliable` при фрагментации. Если пакет несовместим с Unity-профилем — это Open Question оператору, а не повод переписать ADR самовольно.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| **Unity Netcode for GameObjects (NGO)** | Привязывает транспорт к Unity-рантайму: сервер обязан быть Unity-приложением (конфликт с ADR-001), CI на Linux требует Unity-лицензии, `NetworkBehaviour` провоцирует «логику в MonoBehaviour» — ровно тот failure mode, который план запрещает |
| **Mirror** | Высокоуровневый фреймворк со своим жизненным циклом (`NetworkManager`, `NetworkBehaviour`), тянет за собой собственные представления о спавне и состоянии; больше магии, меньше контроля над форматом снапшота (ADR-004) |
| **Сырой `Socket`/`UdpClient`** | Придётся самим писать надёжность, порядок, фрагментацию, keep-alive, MTU — недели работы и класс багов, не относящихся к цели прототипа |
| **TCP / WebSocket** | Head-of-line blocking: потерянный пакет задерживает все последующие; для движения неприемлемо |
| **ENet / Facepunch.Steamworks** | ENet — C-обёртки и нативная зависимость; Steamworks — внешний сервис и аккаунты, вне scope и без бюджета |
| **Вендоринг LiteNetLib исходниками** | Запрещено решением оператора; усложняет обновление и ревью |

## Последствия

- LiteNetLib — библиотека, а не фреймворк: управление сессиями, маппинг peer↔entity, таймауты и реконнект пишем сами (M4/M5). Это ожидаемая работа, а не сюрприз.
- `ITransport` становится замороженным контрактом после M1: замена транспорта не должна трогать `Simulation.Core` и `Server`.
- В интеграционных тестах (M4) сначала используется in-process фейковый транспорт, LiteNetLib подключается в M5 — тесты не зависят от сети и не флапают.
- Риск: проект LiteNetLib поддерживается одним автором. Митигация — абстракция `ITransport` и правило «никаких типов LiteNetLib за пределами `Client.Network`».
