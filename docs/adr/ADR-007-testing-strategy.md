# ADR-007. Стратегия тестирования: unit → replay → integration → load

**Статус:** предложен (ожидает Human-Gate M0)
**Дата:** 2026-11-08
**Связано:** `docs/prototype-plan.md` (M1–M12, финальный чеклист), ADR-001, ADR-003, ADR-004

## Контекст

Исполнитель — flash-модель: код пишется быстро, ошибки дешёвы, но «готово» объявляется преждевременно. Значит, качество должно обеспечиваться автоматическими проверками, а не самооценкой. Одновременно нельзя раздувать тесты «на всякий случай» — план ограничивает объём.

Тесты обязаны идти на `ubuntu-latest` без Unity (ADR-001), быть детерминированными (ADR-003) и не флапать, иначе агент начнёт их «чинить» отключением.

## Решение

**Фреймворк:** xUnit для всего .NET. Причины: `[Theory]`/`[MemberData]` для параметризованных тестов от конфига (M3), параллельное исполнение, минимальная церемония, де-факто стандарт для новых .NET-проектов. Unity-тесты (M6+) — Unity Test Framework, отдельно и позже; в CI они не входят (решение оператора по Unity-Gate).

**Четыре уровня, каждый — свой проект/папка в `src/Tests`:**

| Уровень | Что проверяет | Где | Требование плана |
|---|---|---|---|
| **Unit** | `Simulation.Core` без сети и времени: движение, команды, способности, смерть/респавн, снапшоты, конфиги | `Tests.Unit` | M2, M3, M8 |
| **Replay** | Одинаковый ввод + `seed` → идентичное финальное состояние и тот же хеш состояния | `Tests.Replay` | M2 (1000 команд), финальный чеклист |
| **Integration** | Сервер + фейковый клиент in-process; затем LiteNetLib с потерями/задержкой | `Tests.Integration` | M4, M5, M7 |
| **Load** | N ботов, метрики тика (среднее, p99), отсутствие крашей | `Tests.Load` (+ `tools/bot-client`) | M11 |

**Правила:**

1. **Тест пишется вместе с кодом** (DoD из `AGENT.md` §17): happy path + edge cases + failure cases там, где применимо. Без теста задача не закрыта.
2. **Детерминизм:** никаких `Thread.Sleep` в утверждениях, кроме единственного теста частоты тика сервера (допуск ±0.1 с на 5 с, M4); никаких зависимостей от текущего времени, порядка файловой системы, `Dictionary`-порядка.
3. **Сеть эмулируется детерминированно:** потери/задержка — через обёртку транспорта с фиксированным `seed`, а не через реальный сокет; реальный LiteNetLib — отдельный smoke-тест, помеченный как `[Trait("Category","Network")]`, не в обязательном наборе CI.
4. **Покрытие:** 100% для `Simulation.Tick` и snapshot-методов (coverlet + ReportGenerator, gate в CI). Общий процент по репозиторию — не цель и не гейт (иначе агент начнёт писать бессмысленные тесты ради цифры).
5. **Параметризация от конфига:** тесты, зависящие от баланса, читают `GameConfig` из тестового JSON и не дублируют числа (M3: «изменил JSON → изменился тест»).
6. **Флапящий тест = дефект.** Не `[Ignore]`, не retry, не «пока отключим»: либо чинится причина, либо задача уходит в `blocked` по протоколу 9 (`AGENT.md` §9). Отключение теста без указания оператора — критическая ошибка (`AGENT.md` §11).
7. **Тест как спецификация контракта:** тесты M1 на пустые интерфейсы фиксируют сигнатуры (например, наличие `deltaTime` в `ISimulation.Tick`) — после заморозки контрактов изменение теста означает изменение контракта, то есть ADR.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| NUnit / MSTest | Эквивалентны по возможностям; xUnit выбран за `[Theory]` и параллельность по умолчанию — миграция не даёт выигрыша |
| Unity Test Framework как основа | Требует Unity и лицензию в CI; конфликт с ADR-001 |
| «Пирамида» с большим числом e2e | Медленно и флапает; для прототипа достаточно in-process интеграции |
| Мутационное тестирование / property-based как обязательные | Дорого по времени CI и сложно для агента; допустимо точечно, не как гейт |
| Покрытие «всего репозитория» как gate | Провоцирует тесты ради цифры; gate только на критичные методы |

## Последствия

- CI (M1) запускает `dotnet test` на `ubuntu-latest` для unit+replay+integration(фейковый транспорт); тяжёлые load/network-тесты — по метке, отдельным job'ом.
- Любая задача без тестов не закрывается — это уже в DoD; здесь фиксируется, **какие** уровни обязательны для каких вех.
- Replay-тест — главный инструмент против «недетерминированной симуляции»: он ловит скрытые зависимости от времени/порядка, которые не видит code review.
- Тестовая инфраструктура (`TestFixtures`, эмулятор сети, генератор конфигов) — часть M1/M2, а не «потом»: без неё следующие вехи будут тестироваться вручную.
- Число тестов ограничено задачами плана: «больше тестов» не является целью, цель — покрытие заявленных Gate-проверок.
