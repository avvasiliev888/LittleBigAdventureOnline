# Warrior animation — журнал проблем и доказанных решений

Документ существует по одной причине: за одну сессию одни и те же симптомы
(«висит с поджатыми ногами», «мигает оружие», «плывёт», «смерть не играет»)
возвращались больше десяти раз, потому что причина каждый раз угадывалась,
а не измерялась. Здесь зафиксировано, **что проверять сначала** и **какие
гипотезы уже опровергнуты**, чтобы не тратить на них 11-минутные сборки.

Правило: **сначала число из лога или аудита — потом правка**. Если числа нет,
правка не готова.

---

## 1. Главная причина, которая объясняла почти всё

**Симптом:** персонаж в покое стоит в bind pose («висит с поджатыми ногами»),
смерть не проигрывается, оружие мигает и прыгает, поза не меняется,
хотя `normalizedTime` бежит.

**Причина:** в `WarriorLocomotion.controller` состояние `Idle` ссылалось на
`m_Motion: {fileID: 7400000, guid: c6b9147fbdbe9184a987c18b90ebd031}`.

`7400000` — это адрес **дефолтного пустого тейка** `Take 001` внутри FBX.
Сам клип `1HIdle` имеет **другой** `internalID`, и он записан в meta-файле:

```yaml
clipAnimations:
- name: 1HIdle
  takeName: Take 001
  internalID: 1827226128182048838   # ← вот настоящий адрес клипа
```

Unity резолвит несуществующий fileID в `null` **молча, без ошибки в консоли**.
Состояние с `null`-моушеном не анимирует ничего: персонаж остаётся в той позе,
в которой его оставил предыдущий клип или bind pose скелета.

**Проверка (одна команда):**

```
Unity.exe -batchmode -quit -nographics -projectPath <копия> \
  -executeMethod Albion.Editor.WarriorAnimationProbe.Probe -logFile <лог>
```

Искать в логе секцию `=== 3. CONTROLLER ===` и строку
`*** NO MOTION ***`. Всё, что печатается как `motion=AnimationClip len=…`,
исправно.

**Вылечено:** fileID заменён на `1827226128182048838`.
После правки лог показал `'Idle' motion=AnimationClip len=2,333`.

### Ловушка, в которую я попал дважды

`WarriorControllerFix.Fix()` печатал `bound Idle <- 1HIdle`, но fileID в файле
**не менялся**. Причина: код сравнивал объекты в памяти (`state.motion == clip`)
и пропускал запись, считая ссылку уже правильной. Сравнение объектов в Unity
не говорит ничего о том, что записано на диск.

**Правило:** после любого изменения asset через API — перечитать файл
или прогнать `Probe` и убедиться, что записалось именно то, что нужно.
Не доверять `Debug.Log` из самого скрипта-правки.

## 2. Как устроены адреса клипов в FBX

| Что | fileID |
|---|---|
| `AnimationClip` внутри FBX | определяется его `internalID` из `.fbx.meta` |
| Дефолтный пустой тейк | `7400000` (встречается почти всегда) |
| Корневой объект модели в `BaseMale.fbx` | `1827226128182048838` (в других FBX его нет) |

В `BaseMale@1HIdle.fbx.meta` **оба** значения совпадают с чем-то: `7400000`
это `Take 001`, а `1827226128182048838` — это `1HIdle`. Поэтому подстановка
«правильного на вид» fileID из другого файла даёт молчаливый `null`.

**Правило:** fileID клипа брать только из `internalID` в соответствующем
`.fbx.meta`, никогда не переносить между файлами.

## 3. Реальные причины, найденные по числам

### 3.1 Скорость бралась из команды ввода, а не из перемещения

`UnityView.ApplyEntity` получал `velocity = _predictionVelocity`, а тот
заполняется **раз в 20 Гц тик** из прочитанной команды и обнуляется на тиках
без свежей `MoveCommand`. В результате `speed` мигал `0 ↔ 4,2` внутри одного
состояния `Idle`, а `jumps` (телепорты оружия) вырос до **333**.

**Вылечено:** скорость считается как реальное смещение нарисованного корня
за кадр: `travelled / deltaTime`. Плюс отсечка `MaxSpeed = 12` —
`Idle` получал **29,44 м/с** на кадре возобновления после респавна.

**Проверка в логе:** в `Idle` должно быть `speed=0` и `jumps=0`.

### 3.2 Дёрганье Idle ↔ Locomotion на пороге скорости

Состояние выбиралось голым условием `speed <= 0.1f`. Скорость — это
смещение за кадр, она естественно дрожит около любого фиксированного порога.
Лог зафиксировал **747 переключений** между `Idle` и `Locomotion` за сессию
(~25 в секунду, почти каждый кадр). Клип постоянно перезапускался: ноги
не успевали пройти шаг, тело «ехало» без шагания, всё привязанное к костям
(слоты оружия) мигало.

**Вылечено:** гистерезис в `CharacterVisuals.PlayLocomotionWithHysteresis`:

```csharp
private const float StartSpeed = 0.35f;   // чтобы начать идти
private const float StopSpeed  = 0.10f;   // чтобы остановиться
private const float LocomotionDwellSeconds = 0.18f; // минимум в состоянии
```

**Проверка:** `Locomotion` упал с 22 до 5 за сессию.

### 3.3 Визуалы исчезнувших сущностей не удалялись

`UnityView._entities` только рос. Единственный `Destroy` в файле был для
трупов мобов. При респавне (новая entity id) создавался новый персонаж,
а старый **оставался в сцене навсегда**, застыв в позе первого кадра.
Два воина рисовались друг в друге: один анимированный, второй статуя.

**Как это выглядело в логе:** два `[rig] avatar=WarriorAvatar`; у одного
`changes` растёт, у другого вечно `changes=1`, `head=0,535`, `anchorY=0,793`
(bind pose).

**Вылечено:** `RetireMissingEntities()` + поле `LastSeenFrame` + грейс
`MissingEntityGraceFrames = 30` кадров (полсекунды). Локальный игрок
(`PlayerEntityId`) не удаляется никогда.

### 3.4 После респавна персонаж бежал сам вправо до первого нажатия

**Причина:** игрок умирал, удерживая ПКМ/WASD. `_destinationActive`
не сбрасывался ни при смерти, ни при респавне. Точка назначения была записана
относительно **старой** позиции, поэтому направление получалось произвольным
и обычно указывало прочь от точки возрождения. Первый же тик после респавна
отправлял `MoveCommand` — и персонаж бежал, пока игрок что-нибудь не нажмёт.

Дополнительно: `LocalPredictionSmoother.AddSample` при прыжке больше
`TeleportDistance = 2f` делает `Reset()`, но **сразу же** восстанавливает
скорость из переданного `velocity` — то есть из последней команды.

**Вылечено:**
- `UnityInputSource.ResetHeldInput()` — сбрасывает `_destinationActive`,
  `_destination`, `_abilityPressed`.
- `UnityView.ConsumePlayerRespawnEdge()` — возвращает `true` ровно один кадр
  на переходе мёртв → жив. View — единственное место, которое видит
  авторитетный флаг `IsDead`.
- `ClientRuntime.Update()` вызывает сброс **до** `PollFrame()`.

**Проверка:** умереть, удерживая ПКМ, дождаться респавна — персонаж должен
стоять на месте.

## 4. Гипотезы, которые уже проверены и НЕ подтвердились

Не тратить на них время повторно.

| Гипотеза | Чем опровергнута |
|---|---|
| `animator.Update(0f)` в `LateUpdate` ломает позу | поза не изменилась после удаления |
| `IsMountedEquipment` завышает `meshMinY` | заменено на замер по костям стоп, симптом остался |
| Порог `runSpeedThreshold = 3.2f` виноват | состояние теперь всегда `walkState`, симптом остался |
| `BindHandSocket` роняет риг в bind pose | `[rig] avatar=WarriorAvatar valid=True human=True` |
| `m_WriteDefaultValues` на состояниях | менялось 1/0, разницы в позе нет |
| Слой/вес аниматора | лог: `layer=1,00 animSpeed=1,00 upd=Normal` |
| Аватар повреждён | `[rig] avatar=WarriorAvatar valid=True human=True` |
| `CharacterAimPose` пишет мировые трансформы | он пишет только `_leftHand.rotation` и `_head.rotation`, гейт по луку |
| `RestorePose` через `Animator.Play` | это **создавало** бесконечный Attack; заменено на `Rebind()` |

## 5. Диагностика: как читать лог

`WarriorDiagnostics` печатает строку раз в **0,5 с** на каждый персонаж.

```
[diag] [Character Visual#-2374] t26,6  state=Idle  norm=0,66  speed=0  eq=0
  | footL=0,127 footR=0,131 handL=0,784 handR=0,483 head=0,887
  anchorY=-0,021 meshMinY=0,028(footBones)
  | jumps=0 changes=16 | layer=1,00 animSpeed=1,00 upd=Normal
  hips=0,126,0,601,-0,007 hipsRot=22,5,14,4,324,0
```

Обязательно смотреть на **владельца строки** (`[Character Visual#-2374]`).
До появления этого тега строки разных персонажей были неразличимы, и я мерил
их вперемешку — один застывший воин выглядел как один мигающий.

| Поле | Здоровое значение | Что значит плохое |
|---|---|---|
| `state` | `Idle`/`Locomotion`/`Attack` | `Walking_A(clip)` — это **моб**, не игрок |
| `norm` | плавно растёт 0→1 | стоит на месте → нет моушена у состояния |
| `speed` | `0` в покое, `~4,2` в беге | `0 ↔ 4,2` скачет → скорость из команды, не из движения |
| `head` | `1,35…1,49` | `0,535` → **bind pose** |
| `anchorY` | `≈ 0` (±0,03) | `0,793` → bind pose |
| `jumps` | `0` | > 0 → оружие телепортируется |
| `hipsRot` | не `0,0,0,0,0,0` | все нули → Animator не управляет ригом |

### Ключевая подпись bind pose

```
head=0,535  anchorY=0,793  hipsRot=0,0,0,0,0,0  meshMinY=-0,740
```

Если видите это — искать `*** NO MOTION ***` через `Probe`, а не проверять
аватар, слои и `WriteDefaultValues` в двадцатый раз.

### Клипы мобов в общем логе

`Walking_A` и `Running_A` с **~2388 переключениями** за сессию — это мобы
(`Skeleton_*Controller`, `KnightController`). К воину они отношения не имеют.
`WarriorDiagnostics` висит и на них, поэтому лог выглядит шумным.

## 6. Инструменты

| Инструмент | Что делает | Стоимость |
|---|---|---|
| `Albion/Characters/Probe Warrior Animation` | Печатает моушены всех состояний, импортёр, префаб, сокеты, настройки | **замерено 19.11.2026: ~150 с** на чистой копии, без пересборки клиента |
| `Albion/Characters/Audit Animation Clips` | Метрики каждого клипа: длина, человеческий ли, диапазоны ключевых мышц | ≈ `Probe` |
| `Albion/Characters/Fix Warrior Animation Graph` | Пересобирает переходы и привязывает моушены | ≈ `Probe`, но **проверен плохо** — см. ниже |

Все три — Editor-only, работают на **копии проекта** (живой нельзя, пока открыт
редактор). Копию делать **на `F:`** (`F:\dsh-tmp\...`), не в `%TEMP%`: на `C:`
свободно ~18 ГБ, и это уже давало оборванные и вводящие в заблуждение прогоны.
Пересборка клиента нужна только для изменений в `Assets/Scripts/`.

⚠ **`Fix` рапортует об успехе, не имея что писать.** Дважды подряд
(`[warrior-graph] Rebuilt.`) он отрабатывал на копии **без папки `Assets`**
и «пересобирал» несуществующий контроллер; один прогон закончился
крахом Unity (`1073741845` = `0xC0000409`). Проверка: после любого `Fix`
**перечитать ассет или прогнать `Probe`** — файл на диске должен измениться.
Смотреть на `mtime` контроллера, а не на строку в логе.

**Экономия:** проверять гипотезу через `Probe` (≈3 мин, только редактор)
вместо `build-windows.ps1` (11 мин, полный клиент) — и обязательно **до** билда.

## 7. Чек-лист перед сборкой клиента

1. Есть ли **число** из лога/аудита, которое доказывает причину? Если нет — не собирать.
2. Компилируется ли правка? (`-executeMethod` на копии, искать `error CS`).
3. Все подтверждённые правки собраны в **одну** сборку?
4. Игра закрыта перед сборкой? Иначе `D3D12Core.dll` занят и билд падает с `Access denied`.
5. Свободно ли место на C:? Временные копии съедают ~1,8 ГБ каждая; при `ENOSPC`
   Unity падает на распаковке пакетов, и это выглядит как ошибка кода.

## 8. Что осталось открытым

Замер `Probe` 19.11.2026 подтвердил: граф собран верно, `transitions` ровно как
описано ниже (`Dead`/`BowAim`/`BowIdle` — **0**, остальные — 1), все моушены
живые (`isHuman=True empty=False`). То есть это **осознанный дизайн**, а не поломка.

- `Dead` имеет клип `len=1,8`, `transitions=0` — держит последний кадр;
  проверить, что Animator действительно доходит до состояния.
- `BowAim` (`len=3,767`) и `BowIdle` (`len=5,1`) тоже без переходов — их выбирает код, не граф.
- Слой верхней части тела (`MaleUpperBody.mask`) для стрельбы на бегу не сделан
  (`layer 'Base Layer' weight=1 mask=none` — единственный слой).
- `WeaponKind.Shield` отсутствует.
- Мобы — chibi-заглушки.
- Ресурс `WarriorAnimatorSettings`: `Probe` показывает `prefab=NULL` в разделе
  «SETTINGS ASSET» — либо не назначен, либо не нужен; выяснить при следующей правке.

## 9. ПРОВЕРЕНО 19.11.2026: потеря `internalID` БЕЗОБИДНА

✅ **Тревога закрыта замером, не рассуждением.** Итог: ссылки разрешаются.

Зафиксировано в коммите `0e5caab`. Тогда это было наблюдение по файлам,
а не измеренный факт. Ниже — результат `Probe` на копии проекта.

**Как проверено.** Копия `unity-client` → `F:\dsh-tmp\probe9` (`robocopy`,
без `Library`/`Temp`/`Logs`/`_Recovery`/`.utmp`; **917** файлов в `Assets`),
затем `-executeMethod Albion.Editor.WarriorAnimationProbe.Probe`.
Unity `6000.3.28f1`. Импорт с нуля — **~150 с**, лог **791 КБ**,
`Exiting batchmode successfully`, return code 0.

**Результат (раздел 1 «CLIPS INSIDE EACH FBX» и раздел 3 «CONTROLLER»).**
Все пять «пострадавших» клипов разрешились — не `null`, не пустые:

| Клип | Длина | `human` | `empty` | `motion` в графе |
|---|---|---|---|---|
| `1HWalkF` | 1,1 | True | False | — |
| `1HAttack` | 0,7 | True | False | `AnimationClip` len=0,7, `isHuman=True` |
| `1HCombatRunF` | 0,633 | True | False | — (в `Locomotion` BlendTree) |
| `1HPain` | 0,5 | True | False | `AnimationClip` len=0,5, `isHuman=True` |
| `1HDeathA` | 1,8 | True | False | `AnimationClip` len=1,8, `isHuman=True` |

Плюс `1HIdle` (2,333) — тот, у которого `internalID` сохранился, — тоже `True/False`.

**Вывод.** Гипотеза «без `internalID` Unity резолвит ссылку в `null`» **опровергнута**
для `fileID: 7400000`: позиционное разрешение работает. Потеря `internalIDToNameTable`
после `0e5caab` — косметическая, восстанавливать `.meta` из `HEAD~1` **не нужно**.
Не путать с § 3: там `null` возникал не из-за отсутствия таблицы, а из-за
ссылки на `7400000` там, где клип имеет нестандартный `internalID`
(`1HIdle` = `1827226128182048838`) — и это единственный такой случай, у него поле на месте.

**Побочная находка.** У `BaseMale@1HDeathA` импортёр показывает
`clipAnimations=0`, но `defaultClipAnimations=1` — то есть клип берётся
из default-секции, а не из переопределённой. Работает, но отличается от
остальных пяти; при следующей правке импортёра — не «исправлять» вслепую.

### Историческое описание (оставлено как след)

**Что обнаружено.** После правки шести `BaseMale*.fbx.meta` в них исчезло
поле `internalID` у части клипов:

| Файл | Внутренний ID, на который ссылается контроллер | Есть в новом `.meta`? |
|---|---|---|
| `BaseMale@1HIdle.fbx.meta` | `1827226128182048838` | **да** |
| `BaseMale@1HWalkF.fbx.meta` | `7400000` | **нет** |
| `BaseMale@1HAttack.fbx.meta` | `7400000` | **нет** |
| `BaseMale@1HCombatRunF.fbx.meta` | `7400000` | **нет** |
| `BaseMale@1HPain.fbx.meta` | `7400000` | **нет** |
| `BaseMale@1HDeathA.fbx.meta` | `7400000` | **нет** |

Заодно изменился формат: блок `internalIDToNameTable:` (новый формат Unity 6)
заменён на устаревший `fileIDToRecycleName:`. Размер файлов уменьшился
(`1HWalkF`: 37 933 → 35 770 Б).

**Почему это тревожно.** Ровно этот класс поломки уже стоил часов (§ 3):
состояние ссылалось на `fileID 7400000` вместо `internalID 1827226128182048838`,
Unity **молча** резолвила ссылку в `null`, и состояние не анимировало ничего —
без единой ошибки в консоли. Тогда отсутствие `internalID` и было причиной.

**Почему это может быть безобидно.** Контроллер ссылается на эти пять клипов
именно как `fileID: 7400000` — «первый клип в файле». Для такой ссылки таблица
`internalID` не нужна: Unity резолвит её позиционно. Реально пострадать мог бы
только клип с нестандартным внутренним ID — а он один (`1HIdle`), и у него
поле на месте.

**Как проверить (без полной сборки клиента, ~3 минуты с нуля).**

```powershell
$src = 'F:\Projects\LittleBigAdventureOnline\unity-client'
$copy = 'F:\dsh-tmp\probe9'          # НЕ %TEMP%: на C: свободно ~18 ГБ
robocopy $src $copy /E /XD Library .utmp _Recovery .git obj Temp Logs Builds /NFL /NDL /NJH /NJS /NP
# копия полна, если получилось 917 файлов:
(Get-ChildItem "$copy\Assets" -Recurse -File).Count

& 'N:\Program Files\Unity Hub\Editor\6000.3.28f1\Editor\Unity.exe' `
  -batchmode -quit -projectPath $copy `
  -executeMethod Albion.Editor.WarriorAnimationProbe.Probe `
  -logFile "$copy\probe.log"

# не искать [diag] — Probe пишет блок между этими маркерами:
$c = Get-Content "$copy\probe.log"
$s = ($c | Select-String 'PROBE START' | Select-Object -First 1).LineNumber
$e = ($c | Select-String 'PROBE END'   | Select-Object -First 1).LineNumber
$c[($s-1)..($e-1)] | Select-Object -First 60
```

**Три ловушки, стоившие времени 19.11.2026:**

1. `%TEMP%` больше не использовать — на `C:` всего ~18 ГБ, копии живут на `F:`.
2. `Start-Process`-обёртка возвращает управление **до** Unity: лог обрывается на
   `Application.AssetDatabase Initial Refresh Start`, и это выглядит как падение.
   Ждать `WaitForExit` процесса `Unity`, а не кода запуска.
3. `Probe` пишет через `Debug.Log`, поэтому сообщение стоит **строкой выше**
   трассировки `WarriorAnimationProbe:Probe`. Искать `PROBE START/END`, не `[diag]`.

**Что считать нормой.** В разделе 3 «CONTROLLER» у состояния должны быть
`motion=AnimationClip len=<не 0>` и `isHuman=True empty=False`.
Признак поломки — `motion=NULL` или `empty=True`
(симптом bind pose — § 3, подпись `head=0,535 anchorY=0,793`).

**Что делать при подтверждении** — вернуть `internalIDToNameTable`
(или перезалить `.meta` из `HEAD~1` и повторить импорт), затем перегенерировать
контроллер. На 19.11.2026 подтверждения нет: всё разрешилось.
