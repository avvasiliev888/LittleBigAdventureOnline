# ADR-006. Prediction и reconciliation на клиенте

**Статус:** предложен (ожидает Human-Gate M0)
**Дата:** 2026-11-08
**Связано:** `docs/prototype-plan.md` (M6, M7), ADR-001, ADR-003, ADR-004

## Контекст

При 20 Гц (ADR-003) и RTT 50–100 мс «чистый» серверный авторитет даёт задержку отклика на движение 100–200 мс — это ощущается как «ватный» персонаж. План требует: клиент предсказывает движение, сервер подтверждает/корректирует, при расхождении — откат и повторное применение неподтверждённых команд.

Ограничение: клиент и сервер используют один и тот же `Simulation.Core` (ADR-001), поэтому предсказание — это не отдельная «клиентская физика», а тот же тик на тех же данных.

## Решение

1. **Общий код.** Клиент исполняет `Simulation.Core` локально (только из `Bootstrap`/`Prediction`, ADR-001) с тем же `deltaTime = 1/20` и тем же `GameConfig`.
2. **Буфер истории.** Кольцевой буфер на 128 тиков: для каждого клиентского тика — `(tick, predictedState, appliedCommands)`. Дополнительно — очередь неподтверждённых команд.
3. **Предсказание.** Ввод сэмплируется, команда получает `(ClientTick, Sequence)`, применяется локально немедленно, отправляется серверу.
4. **Подтверждение.** Сервер в каждом снапшоте присылает `LastProcessedClientTick` + состояние. Клиент:
   - отбрасывает команды с `ClientTick ≤ LastProcessedClientTick`;
   - сравнивает своё предсказанное состояние на `LastProcessedClientTick` с серверным;
   - **совпало** (в пределах `EPSILON = 0.01f` по позиции) → ничего не делает (stable network: реконсиляция не срабатывает — отдельный тест);
   - **не совпало** → реконсиляция.
5. **Реконсиляция — откат, не телепорт.** `RestoreFromSnapshot(serverState@tick)` → повторное применение всех неподтверждённых команд по порядку → получить исправленное текущее состояние. Визуально позиция не прыгает: разница между предсказанной и скорректированной позицией гасится сглаживанием (визуальный оффсет, затухающий за 100–150 мс), `transform.position` напрямую не телепортируется.
6. **Порядок команд.** Сортировка по `(ClientTick, Sequence)` — уже требование M2; реконсиляция переиспользует ту же сортировку, а не свою.
7. **Логирование.** Каждая реконсиляция пишется в лог: `tick`, `predicted`, `authoritative`, `delta`, число повторно применённых команд. Это требование Auto-Gate M7 и инструмент отладки оператора.
8. **Что предсказывается:** только движение. Урон/смерть/ресурсы — серверные, без предсказания (достаточно, чтобы не было «отката HP»); при рассинхроне HP клиент просто принимает серверное значение.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Только серверный авторитет, без предсказания | 100–200 мс задержки отклика — провал Human-Gate M7 («движение отзывчивое») |
| «Упрощённая» реконсиляция телепортом к серверной позиции | Рывки, потеря отзывчивости; прямо назван как failure mode в плане M7 |
| Полный откат всей симуляции мира на клиенте (все сущности) | Избыточно: клиент предсказывает только своего персонажа; стоимость и сложность растут |
| Клиентский авторитет движения | Читерство: телепорт/скорость; сервер обязан валидировать (M4) |
| Предсказание урона и смерти | Требует отката чужого состояния и «оживления» — сложность без выигрыша в отзывчивости |

## Последствия

- Требуется **детерминизм в пределах клиентского процесса**: одинаковые входы → одинаковый результат. Кросс-платформенная битовая идентичность с сервером не требуется — расхождение гасится `EPSILON` и реконсиляцией.
- `EPSILON = 0.01f` — часть контракта; менять только с тестом «стабильная сеть → реконсиляция не срабатывает».
- Клиентская копия `Simulation.Core` — тот же код, что на сервере; любое расхождение конфигов (M9) проявится как постоянные реконсиляции, поэтому хеш конфигов проверяется тестом.
- Тест M7 «после реконсиляции позиция совпадает с предсказанной, а не с серверной» фиксирует именно «откат + повтор», а не телепорт.
- Появляется обязанность не аллоцировать в буфере предсказания на каждом кадре (пул/структуры), иначе GC-паузы испортят плавность (M6 Human-Gate).
