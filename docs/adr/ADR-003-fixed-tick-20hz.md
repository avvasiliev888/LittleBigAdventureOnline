# ADR-003. Фиксированный тик симуляции 20 Гц

**Статус:** предложен (ожидает Human-Gate M0)
**Дата:** 2026-11-08
**Связано:** `docs/prototype-plan.md` (M2, M4, M11), ADR-001, ADR-006

## Контекст

Симуляция должна быть детерминированной (M2: «100 тиков с одинаковым вводом → идентичное состояние»), воспроизводимой в replay-тесте и предсказуемой по нагрузке (M11: p99 тика ≤ 50 мс). Движение при этом обязано выглядеть плавно на клиенте при 60+ FPS.

Переменный `deltaTime` (как в типичном `Update()`) делает состояние функцией от частоты кадров и загрузки машины — воспроизведение и сравнение результатов становятся невозможны, а сервер начинает «плыть» под нагрузкой.

## Решение

1. **Фиксированный шаг: 20 Гц, `dt = 0.05 с`.**
   - В `ISimulation.Tick` приходит `float deltaTime`, всегда равный `1.0f / TickRate` для реального сервера; тесты вправе передавать то же значение явно (частота — константа `SimulationCore.TickRate = 20`, а не глобальная переменная).
   - Тик нумеруется целым `uint Tick`, который инкрементируется строго на 1. `Tick` — часть состояния и снапшота.
2. Серверный цикл — «аккумулятор»: `Stopwatch` → накопленное время / `dt` = сколько тиков выполнить; досыпание остатка через `Thread.Sleep` (или `Task.Delay` с точностью до мс) с компенсацией дрейфа, чтобы средняя частота не уезжала. Логика сна — в `Server`, не в `Simulation.Core` (ADR-001).
3. Все длительности в геймплее задаются **в тиках** и конвертируются из секунд конфига один раз при загрузке (`seconds * TickRate`, округление — `MidpointRounding.AwayFromZero`, задокументировано в ADR-005).
4. Клиент рендерит на своём FPS и интерполирует между двумя последними снапшотами (M6); предсказание (M7) выполняется теми же тиками по 20 Гц, независимо от частоты кадров.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Переменный `deltaTime` | Недетерминизм, разное поведение на разном железе, replay невозможен |
| 30 Гц | Больше CPU/трафика и требований к сети без выигрыша для 10–20 CCU; ужесточает бюджет M11 без пользы |
| 60 Гц | Для MMO-подобного движения избыточно: серверный трафик ×3, допустимая задержка ввода не улучшается (её определяет RTT, не тик) |
| 10 Гц | Заметные рывки при интерполяции, задержка ввода до 100 мс, грубая проверка дальности способности |
| Адаптивный тик под нагрузку | Ломает детерминизм и воспроизводимость; деградация должна быть видимой (метрики), а не менять правила мира |

## Последствия

- Бюджет одного тика: **50 мс**; при 20 CCU в M11 средний тик ≤ 25 мс, p99 ≤ 50 мс. Логика тика обязана быть O(сущностей), без аллокаций в горячем пути (проверяется метриками M11).
- Задержка ввода снизу ограничена 50 мс (тик) + RTT; это осознанно: сглаживается предсказанием (ADR-006), а не повышением частоты.
- Числа баланса (кулдауны, каст, респавн) удобнее задавать в секундах в JSON, но хранить/считать в тиках — конвертация в одном месте, покрыта тестом на округление.
- Тест M4 «100 тиков за 5 ± 0.1 с» проверяет именно цикл `Server`, а не `Simulation.Core`; `Simulation.Core` тестируется без сна и без времени.
- Изменение частоты после M1 — изменение замороженного контракта: только через новый ADR и одобрение оператора.
