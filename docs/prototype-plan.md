# План прототипа: архитектура Albion-like MMO

> **Статус:** утверждён. Изменения — только через PR с записью в `docs/adr/`.
> **Связанные документы:** `docs/product-vision.md`, `docs/state.md`, `docs/adr/`.
> **Исполнитель:** DSH на базе deepseek-v4-flash под управлением одного оператора-человека.
> **Инструкция по исполнению:** `AGENT.md` (корень репозитория).

---

## 0. Ключевое допущение об исполнителе

Разработчик — **AI-агент (DSH, deepseek-v4-flash)**, а не человек. Это меняет принципы планирования:

| Человек | AI-агент (flash) |
|---|---|
| Оценка в человеко-днях | Оценка в днях бессмысленна; важна атомарность и проверяемость |
| Держит архитектуру в голове | Ограниченное контекстное окно — задачи должны быть самодостаточными |
| Редко ошибается, дорого | Часто ошибается, дёшево — нужны автоматические gate'ы |
| Чувствует «плохой код» | Не чувствует — нужны явные архитектурные тесты |
| Сам решает «готово» | Склонен объявлять «готово» преждевременно — нужен DoD с автотестами |
| Хорош в «сделай красиво» | Хорош в «сделай по спецификации с тестами»; визуал/фил/баланс — человек |
| Помнит проект | Теряет контекст между сессиями — нужен журнал состояния и ADR |

**Три принципа плана:**
1. **Ни одна веха не закрывается «на глаз».** Gate = Auto-Gate (CI) + Human-Gate (review).
2. **Задачи атомарны** — влезают в контекст агента без потери смысла.
3. **Контракты заморожены после M1** — изменения только через ADR и одобрение человека.

---

## 1. Как читать план

- **Веха (M)** — крупный этап. Закрывается только при выполнении **Gate**.
- **Задача (Task)** — атомарная единица работы для агента, одна сессия.
- **Gate** = **Auto-Gate** (CI, тесты, grep) + **Human-Gate** (проверка человеком).
- **AI-Failure Mode** — типичная ошибка агента на этой вехе и способ её поймать.
- Между вехами — **чекпоинт оператора**: короткий обзор, закрытие/пересмотр ADR, обновление `docs/state.md`. Без чекпоинта следующая веха не начинается.

  - ADR-006: prediction/reconciliation — что именно предсказывается и как сглаживается.
  - ADR-007: стратегия тестирования (unit → replay → integration → load).
- Создать `docs/state.md` по шаблону (см. `AGENT.md`, раздел «Протокол состояния»).

**Auto-Gate:**
- [ ] Все ADR существуют и содержат: контекст, решение, альтернативы, последствия.

**Human-Gate:**

- [ ] Оператор ответил на «Вопросы к заказчику» из Product Vision (или явно отложил).

**AI-Failure Mode:** агент генерирует 20 ADR «на всякий случай». Лечение: ровно 5–7, каждый — одно ключевое решение.

## M1. Walking skeleton: репозиторий, CI, пустая симуляция

**Цель:** каркас, который собирается, тестируется и падает при нарушении архитектуры. **Фундамент, который не переписывается.**

**Задачи для агента (атомарные):**
1. Создать структуру репозитория: `/src/Simulation.Core`, `/src/Shared`, `/src/Server`, `/src/Client.Network`, `/src/Tests`, `/unity-client`, `/tools/bot-client`, `/docs`.
2. Создать `.sln` с проектами и зависимостями:
   - `Simulation.Core` — не зависит ни от чего.
   - `Shared` — не зависит от Unity.
   - `Server` — зависит от `Simulation.Core` + `Shared` + `Client.Network`.
3. Настроить CI: сборка, `dotnet test`, **grep-проверка «в `Simulation.Core` нет `UnityEngine`»**.
4. Реализовать пустые `ISimulation`, `ICommand`, `ISnapshotSerializer`, `ITransport`, `IInputSource`, `IView` с XML-документацией контрактов.
5. Реализовать `SimulationState` (тик, список сущностей: id/позиция/HP), без логики.
6. Написать smoke-тест: `Simulation.Core` создаётся, `Tick` не падает.

**Auto-Gate:**
- [ ] `dotnet build` проходит на чистой машине.
- [ ] `dotnet test` проходит (≥ 1 тест).
- [ ] CI падает, если в `Simulation.Core` добавить `using UnityEngine;` (проверено вручную).
- [ ] Unity-проект открывается и собирается (пустая сцена).
- [ ] `docs/state.md` обновлён: перечислены созданные интерфейсы и их контракты.

**Human-Gate:**
- [ ] Оператор прочитал интерфейсы и подтвердил контракты. **Интерфейсы заморожены.**
- [ ] Оператор вручную проверил, что CI краснеет при `using UnityEngine;` в `Simulation.Core`.

**AI-Failure Mode:** агент «упрощает» интерфейсы (например, `ISimulation.Tick(commands)` без `deltaTime`). Лечение: XML-док контрактов, human-review, заморозка после одобрения.

## M2. Симуляция: детерминированный тик и движение

**Цель:** симуляция даёт **одинаковый результат** при одинаковом вводе. Ядро архитектуры.

**Задачи для агента:**
1. Реализовать `MoveCommand` (направление, `ClientTick`, `Sequence`).
2. Реализовать `Simulation.Tick`: применение `MoveCommand` к сущности с учётом `deltaTime` и `moveSpeed` из конфига.
3. Реализовать `CreateSnapshot`/`RestoreFromSnapshot` (полный снапшот, без дельт).
4. Реализовать сортировку команд по `(ClientTick, Sequence)`.
5. Написать unit-тесты:
   - 100 тиков с одинаковым вводом → идентичное состояние (сравнение по полям).
   - Команды в разном порядке с одинаковыми `(ClientTick, Sequence)` → одинаковый результат.
   - `RestoreFromSnapshot` восстанавливает состояние 1:1.
6. Написать replay-тест: 1000 команд с `seed` → воспроизведение → идентичное финальное состояние.

**Auto-Gate:**
- [ ] Все unit-тесты зелёные.
- [ ] Replay-тест зелёный.
- [ ] CI-grep: нет `UnityEngine` в `Simulation.Core`.
- [ ] Покрытие `Simulation.Tick` и snapshot-методов — 100% (coverlet/ReportGenerator).

**Human-Gate:**
- [ ] Оператор прогнал replay-тест дважды, результат идентичен.
- [ ] Оператор проверил, что `MoveCommand` не содержит лишних полей (`float speedMultiplier` и т.п. — это в конфиге, не в команде).

**AI-Failure Mode:** агент использует `UnityEngine.Mathf` внутри `Simulation.Core`. Лечение: CI-grep, code review, замена на `System.Math` / `System.Numerics`.

## M3. Способность, здоровье, смерть, data-driven конфиг

**Цель:** доказать, что геймплейные параметры живут в конфигах, а не в коде.

**Задачи для агента:**
1. Создать JSON-схему конфигов (`abilities`, `actors`) в `Shared/Config`.
2. Реализовать загрузчик с валидацией (уникальные `id`, числовые диапазоны, ссылочная целостность). Невалидный конфиг → исключение с понятным сообщением.
3. Реализовать `AbilityCommand` (цель/направление, `ClientTick`, `Sequence`).
4. Реализовать логику способности: проверка дистанции, кулдауна, ресурса; урон; установка кулдауна.
5. Реализовать смерть (HP ≤ 0 → `isDead`), респавн через N секунд (N — в конфиге).
6. Unit-тесты:
   - Способность наносит урон в радиусе; **не** наносит вне радиуса.
   - Кулдаун блокирует повтор.
   - Смерть при HP ≤ 0; респавн через N секунд с полным HP.
   - Изменение `damage` в JSON меняет результат теста (параметризованный тест).

**Auto-Gate:**
- [ ] Unit-тесты зелёные.
- [ ] Тест «изменил JSON → изменилось поведение» проходит.
- [ ] Невалидный JSON → падение с понятной ошибкой (отдельный тест).
- [ ] CI-grep: в `Simulation.Core` нет литералов вида `const float DEFAULT_DAMAGE` (эвристика + ручной review).

**Human-Gate:**
- [ ] Оператор изменил `damage` в JSON, перезапустил тест — увидел изменение.
- [ ] Оператор проверил, что в `Simulation.Core` нет hardcoded геймплейных констант.

**AI-Failure Mode:** агент дублирует параметры в коде (hardcoded fallback). Лечение: тест «удалить JSON → должно упасть, а не взять дефолт».

## M4. Сервер: цикл, валидация, снапшоты

**Цель:** консольный сервер, принимающий команды, валидирующий их и рассылающий снапшоты.

**Задачи для агента:**
1. Реализовать `ServerLoop` с фиксированным тиком 20 Гц (`Thread.Sleep` с компенсацией дрейфа).
2. Реализовать `InputValidator`: дистанция, кулдаун, ресурс, лимит частоты команд.
3. Реализовать `ISnapshotSerializer` (полный снапшот, без дельт).
4. Реализовать TCP-транспорт-заглушку для отладки **или** сразу LiteNetLib (см. ADR-002).
5. Реализовать обработку подключения/отключения клиентов, хранение сессий.
6. Интеграционный тест: сервер + фейковый клиент (in-process) → команда → снапшот → состояние соответствует.

**Auto-Gate:**
- [ ] Интеграционный тест зелёный.
- [ ] Валидатор отклоняет: команду вне радиуса, на кулдауне, превышение частоты.
- [ ] Сервер логирует отклонённые команды с причиной.
- [ ] Тик стабилен: 100 тиков за 5 ± 0.1 с (тест).

**Human-Gate:**
- [ ] Оператор запустил сервер + фейковый клиент, увидел снапшоты в логе.
- [ ] Оператор проверил, что валидатор не «съедает» легитимные команды (ложные срабатывания).

**AI-Failure Mode:** агент делает валидатор «мягким» — логирует, но пропускает. Лечение: тест «невалидная команда → состояние не изменилось» + review.

## M7. Prediction и reconciliation

**Цель:** клиент предсказывает движение, сервер подтверждает/корректирует, при расхождении — откат и повторное применение.

**Задачи для агента (самые мелкие — веха сложная):**
1. Буфер истории предсказания (состояние на каждый клиентский тик + неподтверждённые команды).
2. Локальное применение команды к клиентской копии симуляции (предсказание).
3. Обработка `ServerAck` и снапшота: сравнение предсказанного с серверным на подтверждённом тике.
4. Реконсиляция: `RestoreFromSnapshot(serverState)` → повторное применение неподтверждённых команд.
5. Тест: при задержке 100 мс и потерях 20% предсказание сходится за ≤ 3 тика (эпсилон 0.01).
6. Тест намеренного рассинхрона: изменить команду на клиенте → реконсиляция сходится к серверному.

**Auto-Gate:**
- [ ] Тест сходимости зелёный.
- [ ] Тест намеренного рассинхрона зелёный.
- [ ] Лог клиента содержит записи о реконсиляции (для отладки).
- [ ] При стабильной сети реконсиляция **не** срабатывает (тест).

**Human-Gate (критичен):**
- [ ] Оператор с симуляцией потерь/задержки: движение отзывчивое, редкие рывки допустимы, но **состояние сходится**.
- [ ] Лог: реконсиляция срабатывает только при реальных расхождениях.

**AI-Failure Mode:** агент «упрощает» реконсиляцию — телепортирует клиента к серверной позиции (без повторного применения команд) → рывки, потеря отзывчивости. Лечение: тест «после реконсиляции позиция совпадает с предсказанной, а не с серверной» + review.

## Финальный чеклист готовности прототипа

- [ ] `Simulation.Core` собирается и проходит unit-тесты **без Unity**.
- [ ] CI падает при `UnityEngine` в `Simulation.Core`.
- [ ] Сервер использует **ту же** `ISimulation`, что и клиент.
- [ ] Replay-тест с фиксированным `seed` воспроизводит идентичное состояние.
- [ ] При потерях 30% и задержке 100 мс клиент сходится за ≤ 3 тика.
- [ ] Способность и параметры актора — в JSON; изменение JSON меняет поведение без правки кода.
- [ ] В Unity нет MonoBehaviour с авторитетной логикой (CI-grep + review).
- [ ] Демо-сценарий проходит: два клиента, движение, способность, смерть, респавн, «плохая сеть».
- [ ] 20 ботов: тик ≤ 25 мс средний, p99 ≤ 50 мс.
- [ ] README позволяет собрать и запустить с нуля.
- [ ] ADR заполнены, `docs/state.md` актуален.

## Что НЕ входит в прототип

- Полноценная MMO-инфраструктура (регионы, шардирование, балансировка).
- Открытый мир, зоны, инстансы, матчмейкинг.
- Крафт, экономика, инвентарь, торговля.
- Более одной способности и более одного типа противника.
- ИИ противников.
- Аккаунты, БД, сохранение между сессиями.
- Промышленный античит (только базовая валидация ввода).
- Кроссплатформенная сборка (iOS/Android/Xbox) — только desktop + эмуляция «mobile»-профиля.
- Фотореалистичная графика и кастомный арт.
